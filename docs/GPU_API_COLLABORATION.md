# 本地 GPU + API 协作策略

## 目标

Ai Multi Agent 的本地 GPU 模型不是为了替代云 API，也不是为了增加复杂度。它的正确定位是：

```text
本地 GPU 负责预处理、整理、压缩、初步生成和上下文筛选。
云端 API 负责关键决策、高质量生成、复杂工程推理和稳定输出。
```

核心目标有两个：

- 减少传给 API 的无效内容，从而降低 Token 消耗。
- 让 API 收到更精简、更准确、更有价值的上下文。

## 当前已有基础

相关文件：

- `agent/llm_client.py`：自动注册 `ollama`，并管理云端 API Provider。
- `agent/router.py`：检查本地 Ollama 模型，处理 NPU/GPU/API 路由。
- `agent/npu_classifier.py`：轻量快速分类和问候响应。
- `server.py`：`/api/chat` 中处理 `force_api`、`is_escalation`、`autonomy_mode`。
- `agent/workflow.py`：复杂任务执行和工具调用。
- `agent/compactor.py`、`agent/distillation_worker.py`、`db.py` 的 `distilled_knowledge`：上下文压缩和运行日志蒸馏基础。

当前实际链路：

```text
用户输入
  -> NPU 规则快速判断
  -> 本地 GPU/Ollama 尝试处理简单聊天、润色、草稿、联网搜索结果整理
  -> 复杂任务或强制 API 进入 Cloud API / AgentWorkflowEngine
  -> 执行日志进入 run_events
  -> 空闲蒸馏写入 distilled_knowledge
```

## 适合本地 GPU 先处理的任务

- 问候、闲聊、轻量解释。
- 用户输入整理：把口语化需求压成结构化目标、约束、验收标准。
- 上下文筛选：从长日志中提取错误信息、文件名、失败命令、关键堆栈。
- 初步方案草稿：生成不直接落盘的草案和备选路径。
- 报告润色：把已有事实整理成自然语言。
- 搜索结果摘要：在工具拿到网页或检索结果后，本地模型先做粗摘要。
- 历史消息压缩：把旧会话压成简短记忆。
- 运行事件蒸馏：把 `run_events.detail_json` 中冗余日志压成可复用知识。

这些任务的共同特点是：失败成本低、可回退、主要目的是减小上下文和提升可读性。

## 必须交给 API 的任务

- 复杂架构设计。
- 多文件工程修改计划。
- 需要高可靠性的代码生成和重构。
- 需要严格遵守用户约束的比赛交付内容。
- 高风险工具调用前的判断和说明。
- 复杂 bug 诊断、测试失败分析和修复策略。
- 需要稳定格式输出的最终报告。
- 本地 GPU 输出不确定、空泛、跑偏或超时后的兜底。

这些任务的共同特点是：质量要求高、上下文依赖强、错误成本高。

## 推荐协作流程

### 1. 输入整理

本地 GPU 先把用户输入整理为：

- 任务目标。
- 必须保留的功能。
- 禁止改动范围。
- 可能涉及文件。
- 验收标准。
- 是否需要工作区。
- 是否可能需要 API。

整理后的短上下文再传给 API，可以减少原始长口语输入带来的 Token 浪费。

### 2. 上下文筛选

在调用 API 前，只传高价值上下文：

- 最近 3 到 6 条关键消息。
- 当前任务相关文件摘要。
- 最近失败命令和错误堆栈。
- 与当前页面或接口相关的代码片段。
- `distilled_knowledge` 中与任务匹配的摘要。

不要把完整运行日志、完整历史会话、无关文件树全部塞给 API。

### 3. 本地草稿，API 定稿

对复杂任务可以先由本地 GPU 生成粗草稿：

- 可能的文件范围。
- 简短风险提示。
- 初始步骤。

API 只接收草稿和关键上下文，负责最终可执行方案和代码生成。这样 API 不必从零解析大量杂音。

### 4. 执行后蒸馏

任务完成后，把运行事件、错误、修复和结果压缩成：

- 做了什么。
- 改了哪些文件。
- 失败过什么。
- 如何解决。
- 哪些结论后续可复用。

写入 `distilled_knowledge` 或长期记忆，下一次类似任务优先读取摘要，不重复发送完整历史。

## 如何判断是否需要 API

优先走本地 GPU：

- 用户只是问候、解释、改写、总结。
- 不需要写文件。
- 不需要跨多个模块判断。
- 本地模型能在一次短响应中解决。
- 失败后不会破坏项目状态。

直接走 API：

- 用户明确要求深度实现、修复、重构、比赛交付。
- 需要修改核心文件。
- 需要理解多个模块之间的关系。
- 需要稳定格式、严格遵守约束。
- 本地 GPU 返回空泛、幻觉、漏条件或超时。
- 用户启用 `force_api` 或 `is_escalation`。

混合模式：

- 本地 GPU 先压缩和筛选上下文。
- API 负责关键生成。
- 执行结果再由本地 GPU 整理摘要。

## 降低 Token 消耗的方法

- 把完整会话历史压缩成任务摘要。
- 把长日志压缩成错误类型、关键堆栈和失败命令。
- 文件内容只传相关函数、组件或接口，不传整仓。
- Dashboard、Reports、History 等展示数据只传统计摘要。
- 对已解决问题保存蒸馏结果，下次只传摘要和链接文件名。
- 对重复请求先查历史和运行记录，避免重复调用 API。
- 对简单回复使用本地 GPU 或 NPU 快速层。
- API 调用前先检查是否已绑定工作区和是否具备必要信息，避免无效调用。

## 避免误用

- 不要所有请求都直接交给 API。
- 不要让本地 GPU 承担超出能力的复杂工程决策。
- 不要把本地 GPU 生成的草稿直接当最终答案落盘。
- 不要为了省 Token 牺牲比赛交付质量。
- 不要把 API Key、`.env`、密钥文件内容加入上下文。
- 不要把无关日志和缓存目录交给模型。

## 后续可小步增强

不建议大规模重构。可以按小步增强：

1. 在 `/api/chat` 调用 API 前增加“上下文摘要对象”，字段包括目标、约束、相关文件、错误摘要。
2. 让 `distillation_worker.py` 的摘要能按 session 或 run_id 被检索。
3. 在 Dashboard 显示 API Token 节省估算和本地 GPU 命中次数。
4. 给 `route_intent` 增加更明确的 `needs_api_reason` 字段，方便前端展示路由原因。
5. 对同一 session 的重复请求做缓存或复用上次蒸馏摘要。

这些增强都应该保持现有 `server.py`、`agent/router.py`、`agent/workflow.py` 的基本结构，不另起一套复杂调度系统。
