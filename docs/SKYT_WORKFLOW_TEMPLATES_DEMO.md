# 天韬（SkyT） Workflow Templates 比赛演示设计

本文记录 天韬（SkyT） 的 Workflow Templates 比赛演示方案。它面向后续开发者和 AI 编程助手，不是普通用户说明书。

## 演示目标

Workflow Templates 的目标不是保存一张流程图，而是展示 天韬（SkyT） 能把复杂任务转成可执行、可记录、可回放的多 Agent 工作流。

比赛现场要让观众快速看到：

- 用户可以选择预设模板。
- 模板包含多个职责清晰的 Agent 节点。
- 节点之间有明确执行顺序。
- 执行过程会进入运行历史。
- 深度回放可以看到每个节点输入输出。
- 最终结果可以进入报告中心。

## 为什么它是展示重点

普通对话式 AI 容易让过程变成黑盒。Workflow Templates 可以把“自然语言开发”拆成清楚的工程链路：

```text
任务输入 -> 多 Agent 节点协作 -> 执行步骤 -> 结果产出 -> History -> Replay -> Reports
```

这条闭环能体现 天韬（SkyT） 的工程化价值：不是一次性生成，而是可编排、可审计、可复盘。

## 五个推荐演示模板

### 1. AI 工程生成流水线

推荐输入：

```text
帮我生成一个 Python 贪吃蛇小游戏，要求有计分、失败重开和运行说明。
```

节点结构：

- 需求理解 Agent：提取功能点、约束和验收标准。
- 架构规划 Agent：生成项目结构和技术方案。
- 代码生成 Agent：输出核心代码和文件说明。
- 本地检查 Agent：检查依赖、语法风险和可运行性。
- 报告总结 Agent：输出运行方式和后续优化建议。

预期输出：项目结构、代码块、运行说明、检查建议和报告摘要。

展示重点：复杂代码任务不是黑盒生成，而是逐步拆解和可回放。

### 2. 项目文档整理流水线

推荐输入：

```text
请整理当前项目结构，生成一份后续维护和 vibe coding 使用的 Markdown 指南。
```

节点结构：

- 文档扫描 Agent：识别 README、架构文档和优化文档。
- 架构理解 Agent：提取前后端关系、数据流和核心模块。
- 重点压缩 Agent：把长文档压缩成高价值上下文。
- Markdown 生成 Agent：生成维护文档。
- 归档记录 Agent：总结重要结论并进入历史工作记录。

预期输出：文档索引、架构摘要、压缩上下文、Markdown 指南和归档摘要。

展示重点：本地 GPU 可以辅助文档整理和项目记忆，不把长上下文直接塞给 API。

### 3. 问题定位与修复流水线

推荐输入：

```text
页面流式输出时我往上滚会被强制拉回底部，请帮我定位并给出修复方案。
```

节点结构：

- 问题理解 Agent：明确现象、影响范围和成功标准。
- 相关文件定位 Agent：判断可能涉及的前端、后端或样式文件。
- 原因分析 Agent：分析根因和状态流。
- 修改方案 Agent：提出最小必要改动。
- 验证建议 Agent：给出构建、手动测试和回归检查。

预期输出：问题定义、候选文件、根因、修复方案和验证清单。

展示重点：天韬（SkyT） 不是乱改代码，而是先定位、再分析、再修复。

### 4. 比赛演示增强流水线

推荐输入：

```text
请帮我优化 天韬（SkyT） 工作流页面的比赛展示路径，让评委快速看懂多 Agent 协作价值。
```

节点结构：

- 展示目标 Agent：提炼比赛要表达的核心价值。
- UI 重点 Agent：分析页面视觉层级和展示重点。
- 交互简化 Agent：判断哪些复杂功能应弱化。
- 演示路径 Agent：生成现场操作顺序。
- 讲解文案 Agent：生成适合背诵的讲解词。

预期输出：展示目标、UI 强调项、弱化项、演示步骤和讲解文案。

展示重点：天韬（SkyT） 不只是能写代码，也能服务比赛演示本身。

### 5. 本地 GPU 辅助 API 生成流水线

推荐输入：

```text
请为一个 Flask 人员管理系统整理需求并生成 API 调用前的高价值上下文，再给出最终实现方案。
```

节点结构：

- 本地 GPU 初步理解 Agent：快速理解用户需求。
- 本地 GPU 上下文压缩 Agent：压缩历史、文档和无关内容。
- API 请求准备 Agent：整理 API 输入。
- 云端 API 高质量生成 Agent：生成最终方案、代码或文档。
- Token 统计与回放 Agent：记录本地 Token、API Token 和执行步骤。

预期输出：GPU 需求理解、压缩上下文、API 输入、最终方案、Token 与回放摘要。

展示重点：本地 GPU 是 API 的辅助层，不是盲目替代 API。

## 推荐现场演示路径

1. 打开 `Workflow` 页面。
2. 展示 5 个比赛演示模板卡片。
3. 选择 `AI 工程生成流水线`。
4. 展示推荐输入、节点数、GPU/API 标签和节点分工。
5. 点击 `在编辑器中打开`，展示节点按流程展开且职责清楚。
6. 返回模板页，点击 `运行此工作流`。
7. 切到聊天区，展示执行步骤逐步出现。
8. 打开 `运行历史`，选择刚才的 run。
9. 进入 `深度回放`，展示 `WORKFLOW_NODE` 事件、输入输出和 Token。
10. 打开 `报告中心`，展示自动生成的 Workflow Report。

## 演示时应展示的页面

- `/workflows`：模板列表和比赛演示卡片。
- `/workflows/editor`：多 Agent 节点编排。
- `/`：执行步骤和模型路由。
- `/history`：运行记录。
- `/replay/:runId`：深度回放。
- `/reports`：报告中心。

## 演示时应避免的内容

- 不展开过多底层配置项。
- 不展示 API Key、`.env` 或密钥文件。
- 不长时间解释每个按钮。
- 不把本地 GPU 说成完全替代云 API。
- 不在现场执行危险命令或未验证的全局安装。

## 后续优化方向

- 为模板增加更明显的演示模式标识。
- 在运行历史中增加“来自哪个模板”的字段展示。
- 在深度回放中单独高亮模板节点顺序。
- 为报告中心增加 Workflow Template 分类筛选。
- 为每个模板提供一键生成演示脚本。
